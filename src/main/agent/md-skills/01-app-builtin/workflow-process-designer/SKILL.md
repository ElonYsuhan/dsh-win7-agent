# 业务流程设计

这是 Camunda 官方 camunda-bpmn 的离线适配版，建模依据为 OMG BPMN 2.0.2，执行契约以当前 `workflow_catalog` 为准。来源、固定版本、改动和许可见 [references/sources.md](references/sources.md)。不代表本 Agent 已实现完整 BPMN，也不要求安装 Camunda、c8ctl、FEEL 或其他执行引擎。

## 先明确业务，再生成草稿

从用户需求提取：触发条件、参与角色、输入资料、每步动作和结果、完成条件、拒绝/补正路径、执行故障及已发生的外部操作。任务标题使用“动作＋对象”，一个节点承担一个可验证动作；角色可写入说明，不把角色文字冒充系统账号权限。

已有说明足够时直接设计，不重复盘问。只询问会改变流程的关键缺口，例如“退回申请人还是上一审核人”“修改后从哪里重新审核”。明确区分用户确认的规则与待确认假设。复杂流程先给简洁的步骤/分支表和能力缺口；重要规则不明时先确认，不静默简化。

## 驳回是业务路径

设计审批、审阅或补正流程时，读取 [references/rejection-and-replay.md](references/rejection-and-replay.md)。办理使用 `handle`，已阅使用 `review`，批准/驳回使用 `approve`；不要把所有人工节点变成审批，也不要默认替人通过或驳回。

逐个列出：谁可以提出驳回、原因、真实目标节点、哪些结果失效、从哪里重提，以及哪些外部操作需要核查后重放。用户说“重新来过”时先判断是补正、重新审核还是新建业务实例。复杂退回优先绑定明确的上游人工节点 ID；只有“上一人工环节”确实符合业务规则时才用 `previous-human`。

本引擎用实例事实处理退回，定义的正向边仍为 DAG。不要添加反向边造环，不要为了实现驳回再复制一套相同节点。技术超时/接口失败属于故障与重试，不能伪造成业务驳回；历史结果和驳回原因要保留。

## 映射到真实能力

调用 `workflow_catalog` 获取当前节点、模板和能力限制；参考 [references/agent-mapping.md](references/agent-mapping.md)。只生成本引擎可接受的 JSON，不输出 BPMN XML 充当可执行流程。

当前支持 `condition` 排他条件分支和 `merge` 排他汇合，遵循 XOR 首条命中及显式默认路径语义。金额分级等规则必须创建真实 condition 节点并绑定上游结构化字段，不得默认设计成四级全走。规则配置与完整实例见 [条件分支契约](references/conditional-routing.md)。每个出口连一条边，默认分支必填，所有路径到达结束；共用后续步骤前用 merge 汇合，后续数据绑定 merge 输出。未选路径不执行；驳回补正后重新计算选路。AI可提取结构化事实，不代替人工审批或确定性比较。

仍不支持子流程、角色账号自动分派、并行会签/或签、定时升级、自动审批、撤回和补偿。多条普通连线不能冒充这些能力；应明确缺口，不把当前能力描述为完整 BPMN 引擎。

工具/REST/Agent 步骤涉及外部副作用时，明确权限、幂等依据、失败处置和重放确认；Skill 不授予执行权限。AI 可整理与建议，人工审批仍由实际用户完成。

## 结构校验与业务走查

开始可达、结束可达、节点 ID 唯一，字段映射引用真实上游，产物可实际交付；名字最多15字，详细规则写 `description`。调用草稿工具时运行时会校验结构；失败后按错误定点修正，不能宣称仅画出图就通过验收。连续三次无法修复同一问题时，说明剩余问题，停止反复重建。

使用 [references/scenario-review.md](references/scenario-review.md) 走查正常通过、驳回后补正、再次驳回、故障/重试及外部操作重复风险；参考 [references/approval-example.json](references/approval-example.json) 的明确退回目标。区分“设计走查”“模拟”“真实运行”，没有执行证据就不声称真实业务测试通过。设计会话不启动实例、不调用外部业务接口、不批准待办。

首次创建用 `workflow_create_draft`。已有草稿修改先 `workflow_read_draft` 取得完整定义与 revision，再用 `workflow_update_draft` 更新同一 ID，保留未涉及的字段和节点；冲突后重读。用户未要求另建时，不因驳回规则复杂或修复失败而反复创建新流程。

## 交付实际流程

用户让你创建或修改流程时，必须调用草稿工具完成保存，再回读核对。不得用长篇设计说明替代工具操作；需求已明确时不擅自删减审批层级或改变顺序。保存后用简短回复说明流程名称与实际修改，并提示“点击发起流程进入真实待办”。仅对确实影响当前需求的能力缺口作说明，不反复列举无关限制、不再询问用户已经明确的退回规则。设计阶段不自动批准人工节点；实际待办由用户在执行界面办理。没有真实执行证据时，不宣称已测试。

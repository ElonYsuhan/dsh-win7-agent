# 驳回、补正与重提

## 退回规则表

设计时按需说明，不要求用户填一大套固定表单：

| 要素 | 要确定的内容 |
| --- | --- |
| 触发 | 哪个人工审阅/审批节点，依据哪条业务规则拒绝 |
| 理由 | 要求实际操作人填写原因，不由 AI 伪造 |
| 目标 | 已完成的上游人工环节；补正通常回申请人，不一定回上一审核人 |
| 保留 | 历史审批/附件/原因保留；本轮可复用的表单和资料列明 |
| 失效 | 本引擎从退回目标向后取影响范围，创建新尝试；不承诺任意挑选失效步骤 |
| 重提 | 补正完成后沿正向边推进，受影响的审核重新处理 |
| 副作用 | 已发通知、付款、入库等先核查；外部步骤按实例检查点逐个确认后重放 |

## 当前系统语义

- 只有 `human` 且 `interaction.type` 为 `review` / `approve` 才有业务退回。
- 退回目标必须属于同一实例、是当前节点可达的已完成上游人工步骤；不能退回自己、AI 节点、未来步骤或未完成步骤。
- `returnTo: "previous-human"` 是上一人工环节；明确目标用真实节点 ID。
- 图中只保留正向边；退回是带原因的状态事件，不是图上的循环边。
- 系统保存旧尝试和本轮事实，不删除失败/拒绝历史；旧待办 ID 的重复提交应被拒绝。
- 当前受影响节点存在最多10次执行尝试的限制，达到限制交人工判断；不要承诺无限驳回。
- 修改设计定义不会覆盖已启动实例的不可变版本；对正在运行的业务如何处理需说明。

## 常见差异

“材料缺失”→补正人工环节；“审批拒绝”→说明拒绝依据后退回；“接口返回500”→执行失败；“模型超时”→技术故障；“再次发送通知”→新的外部操作，需要核查是否已成功。以上不能混成一个“失败就从头再来”的规则。

驳回退到上游办理节点并补正后，下游 condition 会重新计算，可改走另一分支；旧选路和旧审批保留为历史，当前未选分支标记 skipped。纯条件与汇合可安全重算，已执行的工具/接口等外部步骤仍需核查后确认重放。撤回已完成的外部操作或补偿仍不支持。

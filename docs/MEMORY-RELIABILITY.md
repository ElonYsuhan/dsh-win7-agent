# 内存生命周期排查与修复（2026-10-18）

## 已确认的问题

1. 固定版 LiteGraph 的 unbindEvents 使用了不匹配的回调和 capture 标记；mouse 模式的指针辅助函数还额外绑定裸 down/up/move 事件。旧节点图通过 canvas/document 的监听器继续可达，背景画布没有释放。实际 Chromium108 反复打开编辑20次，修复前 canvas 监听器24→164、document监听器21→41。
2. 模型请求在完成标记后缺少统一的连接结束和数据接收守卫。异常服务器可以继续发送数据，结束后的回调仍继续解析/累积；HTTP错误正文也曾完整保留后才截取显示。缺少响应总体积上限。
3. 知识库预览把原始 Base64 和转换后的 Blob URL 同时存在标签数据中；每个库有标签上限，但库视图数量和总内容大小没有界限，删除库也未完整撤销旧 URL。
4. 工作流仓储把每个历史实例的完整图、节点输出和时间轴全部常驻内存。即使实例数量有上限，也会随历史正文累积占用大量空间。

## 实现边界

- `src/renderer/workflow-canvas.js` 是应用适配层：创建时禁用库内部绘制循环，由应用持有并取消唯一RAF；正确移除 canvas/document 事件、脱离旧图、清理静态活动引用并释放背景画布缓冲。固定vendor及其清单不修改。编辑器隐藏时停止绘制，销毁时完整释放。
- `src/main/agent/llm.js` 统一在完成/失败时关闭请求，后续chunk与行不再处理；错误正文只保留显示所需前缀。单次模型响应网络内容最多32MiB（含流协议、思考和工具参数），超过时明确失败，不自动重试。OpenAI、JSON响应、Ollama沿原服务入口执行，保留UTF8跨chunk解码。
- 知识库标签只保存转换后的文本/URL，删除重复Base64；最多缓存4个库视图，按估算内容量32MiB清理非当前标签，释放Blob。单个当前预览仍受文件读取入口的独立限制，并非整个Chromium进程的32MiB内存硬限制。目录缓存最多64项；删除库立即清理视图。终止的工作流待办表单也不再跨实例保留。
- 工作流仓储仅为pending/running实例持有完整状态；waiting和结束实例保留轻量索引，需要详情或继续时从事实日志恢复。详情LRU最多8条、估算序列化UTF16内容8MiB预算；不是V8进程硬内存上限。后续事实写入使对应缓存失效。完整历史、产物和审阅记录都保留在磁盘，不因内存淘汰删除。waiting恢复、精确提交及不重放外部副作用保持不变。

## 验证证据与范围

- `scripts/workflows-e2e-smoke.js` 在真实Electron Chromium108中获取CDP实际监听器、强制测试GC并循环编辑20次。修复后canvas17→17、document20→20；一次最终采样JS已用堆约2.97MB→2.94MB。数值只覆盖隔离验收页面，不是用户应用总RSS，也不证明所有长期场景都无泄漏。功能回归同时覆盖绘制、平移、连线、会话和人工待办；1000个流式文字片段合并到一个相邻文本节点，减少DOM对象积累，不改变内容和持久化语义。
- `scripts/knowledge-e2e-smoke.js` 在6个真实知识库分别打开图片，创建6个Blob URL后存活4个，旧URL已被撤销，仍能正确解码展示。
- `scripts/llm-stream-smoke.js` 验证OpenAI/Ollama结束后服务端连接关闭、无后续内容进入结果；无换行异常响应超过32MiB会断开并报错，同时保留中文流解码回归。
- `scripts/workflows-smoke.js` 创建24个带大输出的历史实例，验证索引不保留正文、详情恢复完整且LRU数量/预算不越界；已有取消、恢复和实例隔离继续验证。
- 必须执行完整check、内嵌Node16回归和当前平台打包，核对最终源码。Win7真机及长时间真实业务负载仍需验收。

这些修改不引入新依赖、运行时下载或第二个服务容器。事实归仓储、纯状态规则保持独立，平台适配层可以随未来宿主更换而替换。不要通过生产环境强制GC或定时清空用户记录掩盖泄漏；RSS不立即下降也不能单独作为仍泄漏的结论。


## 2026-10-22：长任务流式快照写入放大

用户报告单个任务让 macOS 显示 Agent 占用22.62GB。只读检查时该应用的渲染进程
已经退出，仍存活的主进程和服务采样不再包含故障时的渲染堆，因此没有取得22GB现场
堆快照，不能宣称完整复现了该峰值。对应任务快照约0.76MB，界面仓库约3.35MB。

已确认并通过隔离Chromium108复现的缺陷：每个 assistant:thinking 增量都同步读取
整段DOM的innerHTML、拼接过程快照，再序列化并写入全部会话localStorage，随后
同步整份仓库给服务端。测试保留3MiB历史消息、发送200个短片段，产生202次全量
写入，累计636,016,078个UTF16代码单元；这表示累计序列化/提交量，不是同时驻留
内存或物理磁盘写入量。该链路会放大分配、DOM序列化和存储队列压力。
另外正文delta原先每个片段重新解析全部Markdown、重建DOM和产物预览。

修复只在renderer适配层：思考快照按250ms固定窗口合并，每个会话仅保留最新容器
引用；工具边界立即保存当前会话，回复/结束、视图重建和卸载时冲刷未保存快照，
后台转前台保持会话归属。普通保存入口仍立即写本地，后端事实仓储与Cordis执行
生命周期不变。正文流式阶段增量追加文本，最终回复再解析Markdown及图片/产物。
不强制GC、不清空历史、不修改运行事实或自动重放任何外部操作。

验证：renderer-smoke覆盖旧过程协议、两轮定位、前后台恢复；新增
`npm run check:memory:browser` 在隔离家目录统计真实Storage写入次数、CDP堆大小、
DOM数量，并检查1200个思考片段完整、1000个正文片段不重复生成产物、最终富文本
及会话切换不丢失。测试中的run_command仅为显示事件，不执行命令。
修复后一次1200片段采样为4次写入、12,662,242个代码单元、JS已用堆约42.5MiB；
测量会随调度改变。它证明该放大链路被抑制，不等于所有任务总RSS的硬上限或已经
复现并彻底解释22GB峰值。仍需用户原任务持续负载验收。实现只用Node16/Chromium108
现有能力，无新生产依赖；未来宿主可替换快照调度，核心业务契约保持独立。

## 2026-10-24：启动指纹与模块往返

启动路径原先反复同步扫描代码。开发机一次 UI 指纹读取34个文件、2,366,401字节，
旧应用目录一次包指纹读取250个文件、6,657,094字节；这些不是 Windows 实测耗时。
现在构建阶段生成指纹，运行时读取有界清单，回归用例验证两个消费者合计只读544字节，
并禁止目录枚举；同版本替换、无效清单、旧包和开发模式分别验证。

返回同一条未变且空闲的会话时，复用当前已展示 DOM，不重新解析全部 Markdown，
不保存当前会话 ID 后附带提交整份历史。仍异步核对真实执行状态；运行中、消息/记忆/
时间线/更新时间变化时走原重建路径。只保存一份当前视图快照，启动运行、更新消息和
清空视图时失效，不缓存多份隐藏会话 DOM。扩展列表未变时不重建整套能力卡片。

`scripts/module-switch-e2e-smoke.js` 使用约4.5MB历史、Chromium108，20轮分别打开
能力中心/流程/知识库并回到原会话，验证零次全量历史保存/提交、DOM保持、内容变化
后正确更新。开发机一次60组切换的打开P95约35ms、返回P95约67ms，包含双RAF等待。
这只是该Mac基准的热切换结果，不代表Windows、首次加载或整机启动预算已验收。
`check:memory:browser` 继续覆盖长流式任务及前后台切换，不能用DOM复用掩盖历史丢失。

# 通用工作流引擎方案（V2 方向）

> 面向的场景：给一份**软件的场景文件**，按软件的使用流程自动生成一条流程；
> 以及更一般的「任务拆解 → 需求分析 → 出报告」这类真实工作链路。
> 本文是对 `docs/WORKFLOWS.md` 首版能力的现状分析与下一步设计，不含实现。

## 0. 先回答两个问题

**Q：现有节点能干这些事吗？**

分两种情况：

| 链路 | 现状 | 卡在哪 |
| --- | --- | --- |
| 任务拆解 → 需求分析 → 报告 | **能跑**。三个 `ai` 节点串起来 + `output` 落盘即可 | 无 |
| 在地图 → 在装备 → 配置装备行为 → 推演 → 结束评估 | **跑不了** | 控制流、数据形态、评估 |

后者卡在四处，都不是"模型不够聪明"：

1. **没有控制流**。`flow/workflow-policy.js` 是纯 DAG 校验 + 拓扑排序，
   没有条件分支、循环、汇合、并行。配置有错要回退、推演不收敛要重来、评估不达标要返工——
   这些在当前引擎里都表达不出来。
2. **端口只走文本**。契约里 `edges[].slot` 只有 0/1，`node.text` 是唯一参数。
   「推演」的结果是一组数据（每个装备的行为轨迹），不是一段文字。
3. **没有评估**。只有 `output` 存文本，没有断言/评分/达标判定，
   「结束评估」既不能表达成节点，也不能作为流程的结论。
4. **AI 节点禁用工具**（`workflow-nodes.js` 里 `tools: []`），
   所以"读场景文件""查装备库""写报告"这类动作在流程里做不了。

**Q：节点的能力该由 Skill 提供吗？**

一半对。必须区分三类东西，它们归属不同层：

| 东西 | 归属 | 理由 |
| --- | --- | --- |
| **控制流**：分支、循环、汇合、并行、超时、重试、人工介入 | **引擎原生** | 必须是确定性的、可复现的、可回溯的。不能交给模型"看着办" |
| **领域知识**：这一步该看什么、产出什么、用什么口径 | **Skill** | 会变、会复用、会由业务同学写。Skill 天然是 Markdown 指南，适合挂到步骤上 |
| **副作用**：读写文件、查库、调外部系统 | **工具 / 插件 / MCP** | 要权限、要幂等、要审计。流程节点只做"受控调用"，不做自由发挥 |

一句话：**Skill 提供"这一步做什么"，引擎提供"按什么顺序、在什么条件下做"，工具提供"动手"。**

## 1. 五层模型（首版只有中间两层的一半）

用户给的三层关系（能力提供方 / 编排节点 / 触发器）是对的，但缺了两层，
而缺的那两层恰好就是这个需求的痛点：

| 层 | 职责 | 首版现状 |
| --- | --- | --- |
| ① 触发层 | 手动 / 定时 / 事件 | 仅手动 |
| ② **编排层（控制流）** | 顺序、分支、条件、循环、并行、聚合、子流程 | ❌ 只有线性 DAG |
| ③ **步骤层（节点）** | 一小步做什么 | 仅 input / template / ai / output |
| ④ 能力层 | Skill（知识）/ 工具（副作用）/ 数据源 | ✅ 已存在，但没接进流程 |
| ⑤ **产物与评估层** | 报告落盘、断言评分、人工签收 | 仅 output 存文本 |

## 2. 设计判断：不要把流程"编译"和流程"执行"混在一起

「给一份场景文件 → 生成流程」本质是**流程的自动编排（compilation）**，
不是节点执行问题。设计上必须把它当成独立的一等能力，且遵守三条：

1. **产物是草稿，不是真相**。生成出来的流程落到画布上供人审阅，人可以改节点、换 Skill、删步骤，
   确认后才保存为正式定义。绝不让 AI 生成的流程直接开跑。
2. **生成过程可见**。每一步"为什么生成这个节点"要能看到（至少把推断出的 Skill 绑定和步骤理由记在节点描述里）。
3. **生成用的是现成的 Agent 能力**，不新造一套 LLM 调用路径。
   现有的 `agent-loop` + 工具 + Skill 足够跑这件事，输出一个符合 `contracts/workflows` 的 JSON 即可。

## 3. 分阶段方案

每阶段独立可交付、独立验收，不做半截的引擎。

### P0：让引擎能"控"（控制流 + 结构化数据）

目标：把 `input → 拆解 → 分析 → 报告` 变成一等公民流程，而不是一串 AI 节点。

- **契约升到 `version: 2`**（现有 `version: 1` 流程**不受影响**，继续按 v1 校验与执行）。
  - 新增节点类型：`condition`（条件分支）、`merge`（分支汇合）、`iterate`（批量/循环）、`assert`（断言/评估）。
  - 端口从「只有 slot 0/1 的文本」放宽为 **具名端口**（`in:0`、`in:1`、`out:ok`、`out:fail`）。
  - `node.params` 结构化参数对象（现在只有 `node.text`），保留 `text` 兼容 v1。
- **值类型**：节点输出可以是 `string` 或 `object`。模板节点支持 `{{input.a.b[0]}}` 路径引用。
- **执行策略**（`workflow-policy.js`）从"拓扑排序 + 逐个执行"扩展为
  **小型解释器**：求值当前节点 → 按输出端口选择后继 → 汇合节点等齐所有入边 → 循环按 `iterate` 策略。
  保持"单实例串行、跨实例并发 2"的现状不变，先不引入节点级并发。
- **验收**：
  - `workflows-smoke.js` 增加：条件分支走到哪条边、循环上限、断言失败后的状态、v1 流程在新引擎下行为不变。
  - `workflows-e2e-smoke.js` 在真实 Chromium 里跑一条带分支和断言的流程，断言产物与实例详情。

### P1：让能力进得来（Skill 节点 + 工具节点）

目标：步骤的"专业性"由 Skill 提供，副作用由受控工具提供。

- **`skill` 节点**：绑定一个已启用 Skill，通过 `skillLibrary.read()` 把正文作为该步的系统提示。
  与 `ai` 节点的区别：`ai` 是通用一步，`skill` 是"按这份领域规范处理输入"。
- **`tool` 节点**：调用一个已注册的工具（插件工具 / MCP / 命令），显式声明：
  - 幂等性（可重放 / 不可重放）
  - 所需权限（沿用 `unattended-policy` 的白名单与拒绝语义）
  - 超时与输出上限
  **硬约束**：引入副作用前必须先定义"重启后如何恢复"——首版的原则是
  **不可重放的外部副作用一律不自动重放**（沿用现有"未完成实例标 interrupted，绝不自动重放"的原则）。
- **AI 节点解除 `tools: []`**：改成可选的受控模式——默认仍为纯文本；
  勾选后允许在**单步内**调用指定白名单工具，权限与限额复用 `tasks.js` 的 `runUnattended` 那套。
- **配置零重复**：节点直接读能力中心里已启用的 Skill / 工具 / MCP 状态，不在流程里重配环境。
- **验收**：`workflows-smoke` 覆盖 skill 注入与工具白名单拒绝；e2e 里断言"AI 节点勾了工具后确实调用了，没勾时没有 tool_calls"。

### P2：场景 → 流程（自动编排）

目标：给一份场景文件，产出一条可审阅的流程草稿。

- **入口**：能力中心新增「场景导入」，或工作流页面里的「从场景生成」。
- **产物**：一份 `contracts/workflows` 的 v2 JSON + 每个节点的建议 Skill 绑定。
- **落点**：直接进画布（未保存状态），用户在画布上改完再保存。生成失败/不可信时给理由，不硬塞。
- **依赖**：P0 的结构化端口（否则生成不出带分支的流程）、P1 的 skill 节点（否则绑不了领域规范）。
- **验收**：给一份真实的场景文件，断言生成的流程能通过契约校验、能在画布上打开、
  执行后产物符合场景的预期结构。

### P3：触发与产物闭环

- 定时任务里可选「执行某条工作流」→ `workflows.run({ id })`（正向）。
- 工作流里可加 `task` 节点，动作触发拉起一个已有任务（反向）。
- 报告产物：`output` 支持 `format: markdown`，实例详情直接内嵌渲染，不必下载再看。
- 人工介入：节点可标记为 `human`，实例停在等人确认的位置（对应"结束评估"里的人工签收）。

## 4. 边界与不变式（每阶段都要守）

- **能力中心零重复配置**：流程读同一份启用状态与权限，不另存一套。
- **不新增生产依赖**：仍要满足 Win7 / Electron 22.3.27 / Node 16.17.1 / Chromium 108。
- **契约版本化**：v1 流程与实例永远可读、可执行；新语义只在 v2 生效。
- **执行事实不重放不确定副作用**：这是首版就有的原则，新增工具节点不得破坏。
- **渲染进程不碰模型与节点执行**：统一走 Cordis 服务。
- **失败要可读**：每个节点的状态、输入输出、错误原因都要能在实例详情里看到。

## 5. 建议的落地顺序

如果只做一件事，做 **P0**。理由：它把"流程"从一串提示词变成真正的编排，
而这个需求（场景文件 → 流程、拆解 → 分析 → 报告）的每一步都是"多步 + 有条件 + 有结论"，
没有 P0 就算接了 Skill 也只是把复杂度塞进提示词里。

P1 紧随其后，因为 Skill 挂载是"步骤专业性"的正确来源；
P2 依赖前两者，最后做；P3 是运营能力的补齐，可以按实际需要排期。

# Agent 自我验证能力方案（v1，待评审）

目标：给定一句需求，Agent 能自己**拆解 → 落地 → 验证 → 修补 → 再验证**，最后交一份可复核的 TestReport。
约束不变：Win7 SP1 x64 可跑、全内网离线、零原生模块、不引入联网下载。

---

## 一、现状盘点：已经有的是什么

| 层 | 能力 | 位置 | 状态 |
|---|---|---|---|
| 执行 | read_file / write_file / edit_file / search_files / run_command | `src/main/agent/tools.js` | ✅ |
| 浏览器 | `browser_launch` / `browser_act` / `browser_eval`（CDP 驱动自带 Electron/Chromium 108） | `builtin/browser-tools` 插件 | ✅ |
| 测试协议 | TestCase（steps + assertions）+ 9 类断言 + TestReport（步骤/断言/console/network/截图） | `src/main/agent/test-runner.js` | ✅ |
| 采集 | console.error、JS 异常、HTTP≥400、失败请求，自动增量记账 | `src/main/agent/browser-driver.js` | ✅ |
| 上下文 | 压缩器（阈值 0.8，逐条截断 + 摘要 + memory） | `src/main/agent/context-compressor.js` | ✅ |
| 扩展点 | 插件注册工具 / 追加系统提示 / 事件总线 | `src/main/plugins/*` | ✅ |

**结论：你说的「browser use 插件」已经落地（R25），它解决的是"能看能点"；真正缺的是"跑得起来、记得住、停得下来、判得准"这四件事。**

## 二、缺口清单（本方案要补的）

| # | 缺口 | 后果（现在的实际表现） | 优先级 |
|---|---|---|---|
| G1 | **没有进程生命周期工具**：`run_command` 只有前台执行 + 最长 10 分钟超时，会话结束后进程去向不明 | 起了 `npm run dev` 就没法继续干活；改完代码无法"重启"；无法停掉残留进程 | P0 |
| G2 | **没有"等服务就绪"原语**：靠 wait 元素或手写 curl 轮询 | 启动类任务经常在服务还没起来时就开始测，误判 FAIL | P0 |
| G3 | **没有任务账本**：需求 → 验收标准 → 步骤 → 每轮结果只存在对话里 | 长循环 + 上下文压缩后"忘了要验什么"，或反复验同一条 | P0 |
| G4 | **循环编排只有一句提示词约束**（"最多 5 轮"写在工具描述里） | 模型可能：不收敛地重复同一失败、或改一行就宣称完成、或忘了回归旧用例 | P0 |
| G5 | **验证手段没有矩阵**：不知道项目自带什么检查（lint/typecheck/test/build）、健康检查在哪 | 每次瞎猜验证方式；漏跑项目原有测试造成回归 | P1 |
| G6 | **失败报告不含定位线索**：只有"哪个断言挂了 + actual 值" | 模型要自己从 0 猜改哪里，改错率高 | P1 |
| G7 | **测试用例不沉淀**：用例写在对话里，会话结束就散了 | 同一个验证每次重写；无法回归 | P1 |
| G8 | 视觉验证（截图 → 视觉模型） | 未做 | P2（按你原计划后置） |

## 三、方案：三次交付

### P0：闭环跑通（必需，第一个迭代）

**A1 · 进程工具**（新增 `start_process` / `stop_process` / `list_processes`）
- 后台 spawn（`shell: true`、Windows 走 cmd.exe、`windowsHide`），**不阻塞**工具调用；
- 每个进程有 `name`（如 `dev`、`api`），环形日志缓冲（256KB，复用终端模块的做法），日志可被 Agent 读取/搜索；
- `stop_process` 杀进程树（Windows `taskkill /T /F`，其余 `process.kill(-pid)`）；
- 会话结束 / 服务退出时统一回收自己拉起的进程；**不碰不是自己启动的进程**；
- 权限沿用 `command` 级（完全访问模式放行、受限模式询问）。

**A2 · 就绪等待**（`wait_ready`）
- 入参：`url` 或 `port` + `timeoutMs`；
- 内部：HTTP GET 轮询（默认 500ms 间隔）直到 2xx/3xx 或超时；TCP 连通兜底；
- 返回实际耗时与最后状态码，便于区分"服务没起来"和"服务起来了但接口错"。

**A3 · 验证账本**（工作区 `.agent/validation/<task-slug>.md` + `.json`）
- 内容：需求原文、**验收标准（可判定的句子）**、验证手段清单、每轮结果（时间/命令/结论/失败原因）、最终结论；
- Agent 每轮开始前 `read_file` 账本、结束后追加——这是"上下文压缩后还记得要验什么"的载体；
- 账本是纯文件，可被用户直接看和改。

**A4 · 循环编排规则**（插件追加系统提示，硬约束）

**完成判定（怎么算"搞好了"）—— 先立这条，其余都是它的推论：**
1. 完成 = **验收标准被真实运行的证据满足**，不是"代码改完了"。验收标准必须可判定（"新增后列表多一行 / 接口返回 200 / 状态字段为真"），判不了的句子先降级成能判的；
2. **只认工具的真实返回**，禁止自称成功（系统提示已有同款条款）；
3. 改完必重跑**同一验证**；收尾必须跑一遍**既有用例**防回归；
4. 验不了的**明写"未验证"**，不许含糊过去。

**循环规则：**
1. **禁止只改不验**：改了代码必须跑对应验证才算完成；
2. FAIL → 先定位（读报告 + 相关文件）→ 改 → **重启受影响的服务** → 重跑同一用例；
3. **轮次预算按失败性质分档**（不是简单数轮）：
   - 断言过严 / 服务未就绪 / 用例写错 → **不计入修复轮次**（先修验证本身）；
   - 代码类失败 → 记 1 轮；
   - **连续 2 轮同一断言同样失败 → 立即停**，不消耗剩余预算：要么换策略（改验证手段/修正断言），要么直接交人；
4. **每轮必须留下增量证据**（这轮比上轮多知道什么）；没有增量 = 无效轮，直接停；
5. 预算：默认 **3 轮自动修复 + 1 次换策略重试（合计 4 次执行）**，硬上限 8 轮但**不期望用满**；
6. 超预算仍失败 → 停下来，交出 FailureReport（含已试过的方案与证据），让用户决策，**不静默放弃**；
7. 完成时输出最终 TestReport（PASS/FAIL + 用例 + 证据链），并写明"哪些验过、哪些没法验"。

### P1：提高一次通过率

- **B1 验证矩阵探测**：进入任务时自动发现——`package.json` 的 `lint/typecheck/test/build` 脚本、服务健康接口（`/api/health`、`/health`）、前端可访问 URL、项目自带测试目录；结果写进账本，作为验证手段的默认顺序（静态 → 单测 → 接口 → DOM/状态 → console/网络 → 截图）。
- **B2 断言补齐**：`http_status`（直接打接口，不经浏览器）、`command_ok`（跑项目自带脚本并断言退出码/输出）、`log_contains`（进程日志）、`file_contains`（产物落没落）。
- **B3 失败定位提示**：断言支持可选 `hint`（相关文件/符号），失败时报告里直接给候选位置；无 hint 时自动 `search_files` 找相关符号。
- **B4 稳定性判定**：连续两轮"断言全过 + 截图哈希一致" → 标记稳定；截图变了但断言全过 → 提示人工看一眼。

### P2：可复用与可维护

- **C1 用例沉淀**：`tests/*.test.json` 版本化；Agent 先读已有用例（复用优先），再决定新增；
- **C2 打包成插件**：以上能力收进 `builtin/self-validate` 插件（与 browser-tools 同级），设置里可整体禁用；
- **C3 视觉验证**：等模型支持 vision 后再加"截图 → 视觉判断"，在此之前判定**一律走 DOM/API/日志**。

## 四、验证手段矩阵（回答"WorkBuddy 的多重验证"）

| 层级 | 手段 | 你的 Agent 靠什么 | 现状 |
|---|---|---|---|
| L1 静态 | 类型检查 / lint / build | `run_command` + 项目自带脚本 | ✅ 有工具，缺 G5 的"知道跑哪个" |
| L2 单测 | 项目自带 test | 同上 | ✅ 同上 |
| L3 接口 | 健康检查 / 接口状态码 | `wait_ready`（待做）+ `http_status` 断言 | ⚠️ G2 |
| L4 运行时状态 | DOM / 应用状态读取 | `browser_eval` + `eval_expr` 断言 | ✅ |
| L5 运行时异常 | console 错误 / JS 异常 / 网络失败 | 自动采集 + `console_clean` / `network_clean` | ✅ |
| L6 进程日志 | 服务端报错 / 启动日志 | 进程日志缓冲 + `log_contains`（待做） | ⚠️ G1/B2 |
| L7 视觉 | 截图 | `screenshot` 落盘（人工看） | ✅ 落盘；视觉判断 P2 |
| L8 回归 | 重跑既有用例 | `test_run` 批量 | ✅ 有，缺"收尾必跑"的编排约束（A4-4） |

判定优先级（沿用你原计划）：**DOM/API > 进程状态/日志 > 截图 > Computer Use**。Computer Use / OCR / 纯视觉定位：不做。

## 五、验收标准

### P0 验收（端到端 demo，可复现）
用一个真实小项目跑完整链条，全程只给一句话需求：

1. 改一处代码 → `start_process` 起服务 → `wait_ready` 通过；
2. `test_run` 跑用例（DOM 断言 + eval 断言 + console_clean + network_clean）；
3. 故意留一个 bug → 报告 FAIL，且**报告能指出失败断言与 actual 值**；
4. Agent 自动定位 → 改码 → `stop_process` + 重启 → 重跑 → PASS；
5. 产出：`TestReport`（终态 PASS）+ 账本文件 + 截图；
6. 冒烟脚本 `check:selfvalidate`（真起 Electron + 真起子进程 + 真改文件），进 `check:*` 家族（不进默认链，与 drag/browser 同级）。

### P1 / P2 验收
- P1：矩阵探测在示例项目上能自动列全脚本；`http_status`/`command_ok`/`log_contains` 各有正反用例；
- P2：插件可禁用（禁用后退化现状不炸）；`tests/*.json` 复用示例 + 回归跑法写进 README。

## 六、风险与边界

| 风险 | 说明 | 处置 |
|---|---|---|
| 目标系统前端过新 | 内核上限 Chromium 108 | 验证范围限定在 108 能跑的系统；更新的由用户换机或换方案 |
| 进程残留 | Win7 无 job object | `taskkill /T /F` 杀树；服务退出钩子统一回收；只回收自己启的 |
| 上下文膨胀 | 验证循环很吃 token | 账本外置 + 紧凑报告（已有 compactSuite）+ 逐条截断（已有） |
| 断言写太松 | 假绿（历史教训：220/589 都过">100"） | 用例评审要点：阈值写比例、断言要有反例 |
| 双端并发 | 一个工作区多个会话同时改 | 本轮不做并发锁；账本按任务分文件，冲突时提示 |

## 七、已定决策（2026-09-23）

| 项 | 决定 | 理由 |
|---|---|---|
| A1 进程工具权限 | 跟随现有 `command` 级：完全访问免审批、受限模式询问；但 `stop_process` **只能停自己启动的进程** | 与 run_command 一致，不增加新的心智负担；回收权限缩避免误杀用户进程 |
| A3 账本位置 | `.agent/validation/<task>.md`（隐藏目录，可 .gitignore） | `tests/` 放可复用的用例（人的资产），账本是每任务一次的过程产物，生命周期不同不混放 |
| A4 轮次预算 | 默认 **3 轮自动修复 + 1 次换策略重试**（合计 4 次执行），硬上限 8；非代码类失败不计轮；**连续 2 轮同样失败立即停** | 轮次上限是保险丝不是收敛机制；真需要 5 轮以上通常说明方向错了，早停报人比烧上下文有价值 |

## 八、推进顺序

1. 先 P0（A1→A2→A3→A4），做完就能演一条完整闭环；
2. 拿真实项目跑 demo，按暴露的问题定 P1 的优先级；
3. P2 等 P1 稳定后再收口成插件。
